# Seller verification admin workspace

Open Admin → Sellers. The workspace uses real seller profiles and audited Didit decisions; there are no demo records in the application.

- Signed Didit status webhooks update the identity state and an allowlisted summary in the existing private `platform_config` table (`didit_review:<user_id>`). The state, summary, notification, and audit event commit together. Production ignores non-live events. Duplicate/stale events cannot replace newer results.
- Only identity summaries are persisted: per-check statuses, name, country, document type and last four characters. Passport/selfie images, full document numbers, date of birth and raw provider responses are not stored. Account deletion removes the summary.
- Admin → Load secure Didit report explicitly calls `GET /v3/session/{session_id}/decision/`. Its response is checked against the profile's session and allowlisted before returning. Provider images are exposed only on trusted Didit/AWS hosts and only in the authenticated response. The action is audited; the response uses `Cache-Control: no-store`.
- Approval and rejection use the owner's exact English messages, defined once in `seller_verification.DECISION_MESSAGES`. Only requests for more information require a manual note. Identity approval does not automatically enable selling. Approval requires a verified email, a verified phone, an active account and a verified Didit identity. A reviewer cannot approve their own account, and a changed session requires a fresh review. Decisions commit atomically with their audit event, bell notification and email outbox record.
- Search, country/status/date filters and server-side pagination work on all seller states, including approved and rejected sellers. Summary cards show all-time totals; the date filter applies to the request queue. The chart shows actual daily audit event counts for seven days, not fabricated growth. CSV export respects filters and excludes full identifiers; up to 5,000 filtered records can be exported at once.
- Existing sessions with no stored summary show unavailable checks until an admin explicitly loads their secure report. Loading a report does not itself enable selling or replace the signed webhook verdict.

No new database migration is required. Existing Didit API/workflow/webhook configuration is reused. This change does not alter the Didit workflow or provider settings.

## Account contact details and phone verification

**Currently paused:** `PHONE_VERIFICATION_ENABLED` defaults to `false`. Phone UI and setup redirects are hidden, OTP endpoints refuse requests, and phone verification is not required for Didit or admin approval. Email verification, email contact forwarding to Didit, seller decision emails and bell notifications stay enabled. Existing phone records and the complete OTP implementation are retained. To re-enable later, activate Didit messaging, set `PHONE_VERIFICATION_ENABLED=true` on the server, and redeploy.

- Email registration first verifies the account email and then opens `/#contact-details`, a separate phone setup page. Google/Facebook sign-in also opens this page when a verified phone is missing. Existing password sign-in continues to open Home; Account settings links to the phone page. A seller must finish phone verification before starting a new identity session or receiving admin approval.
- The page offers a searchable worldwide country selector, validates national phone formats with libphonenumber metadata, and offers SMS and WhatsApp, then a code entry step, resend cooldown and number change. `POST /api/phone/send` calls Didit's `/v3/phone/send/`; `POST /api/phone/check` calls `/v3/phone/check/`. No SMS is sent by the website itself, and there is no local bypass or hard-coded accepted code. Didit can fall back from WhatsApp to SMS.
- The account's verified email and phone are passed to new identity sessions via `contact_details`, with Didit invitation emails disabled to avoid a second set of status emails. Client-supplied email/phone values in identity requests are ignored. Existing Didit sessions cannot be retroactively changed by this setting. Admin details show the account contacts and their verification state.
- Phone numbers and verification markers use private `platform_config` keys `account_phone:<uid>` and `account_phone_verified:<uid>`. The temporary challenge uses `account_phone_challenge:<uid>`, contains the provider session and a five-minute expiry, and never contains the OTP. No raw phone report, code, carrier details or code lifecycle is persisted. Account deletion clears all three keys; personal data export includes the account phone and verification state.
- Send/check endpoints require a signed-in, email-verified account, with existing CSRF protection, user/IP/number limits, a 60-second resend cooldown and at most three local code attempts per provider challenge. Approval must match the saved provider request, opaque account reference and exact phone. An expired or consumed challenge cannot be replayed. Profile updates cannot bypass OTP to change the number.

### Activate real SMS / WhatsApp delivery

Didit requires the organisation's first balance top-up before phone verification is available. Free KYC checks do not activate this paid messaging service. In Didit Business Console, use **Top up balance** (Russian: **Пополнить баланс**), review the amount and message pricing, then complete the top-up yourself. No balance has been topped up by this implementation.

The existing **live** Didit application API key must be available as server-side `DIDIT_API_KEY`. Sandbox keys do not deliver real messages and cannot complete this production phone binding. Once activated, open `/#contact-details`, use a number you own, choose SMS/WhatsApp and enter the received code. Do not send the code in chat. Before activation, a provider `403` is shown as a clear activation error; the UI never claims a code was sent.

Official contracts: [create session](https://docs.didit.me/sessions-api/create-session), [send phone code](https://docs.didit.me/standalone-apis/phone-send), [check phone code](https://docs.didit.me/standalone-apis/phone-check).

## Decision email delivery

Seller decision messages are transactional and use the same persisted body in the bell and email, independent of discovery email preferences. A targeted delivery is attempted only after the decision commits. Duplicate approval/rejection submissions do not create a second notification or email. The existing email worker retries failed verification emails up to three attempts, and Resend receives the same notification-based idempotency key on every retry. Ambiguous `sending` records remain for operator review rather than being automatically re-sent. Provider acceptance is not proof of Inbox delivery; verify that separately with a real approved seller.

Validation: `python -m unittest tests.test_account_contacts tests.test_seller_verification tests.test_identity_service tests.test_email_service tests.test_catalogue_experience`; `npm run build`; `node --test tests/frontend.test.cjs`. PostgreSQL query compatibility can be checked with `SENTRYLOOT_TEST_POSTGRES_READONLY=1 python -m unittest tests.test_seller_verification_postgres`. OTP and email tests use mocked provider responses against isolated storage; they do not send real messages. HTTP tests and localhost Chrome checks should use an isolated database, never production seller records.

The same failure was reproduced on unmodified HEAD a0dcffa; it is unrelated to these changes.
